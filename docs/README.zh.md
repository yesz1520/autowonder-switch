# 文档维护约定

[English](README.md) | 中文

<a id="pairs"></a>

## 配对约定

仓库首页 `README.md` 使用中文，英文版为 `README.en.md`，共用 `README.i18n.yaml`。两种语言都可以先改。`docs/` 下的读者文档沿用以下命名，新增、移动或删除时一起处理三个文件：

- `name.md` 是英文正文。
- `name.zh.md` 是中文正文。
- `name.i18n.yaml` 记录上次一起核对过的两篇正文的 Git blob 哈希。

两篇正文都在一级标题后空一行，放上到另一版的链接，格式见本页页首。保留相同的章节层级、显式锚点、表格形状和代码示例。仓库链接在各自版本中指向对应语言的页面。

<a id="voice"></a>

## 写作约定

从读者眼前的问题写起。说明一条命令时，写运行条件、会改哪个文件，以及如何看出它成功了。遇到“提升可靠性”“便于维护”这样的概括，看看读者还缺哪个事实。如果上一句已经把行为讲清楚，就删掉这句。设计过程留在讨论里；会影响读者选择的原因才放进正文。引用第三方行为时，链接到核对过的源码版本或官方文档。

例如，“使用 `--record` 可以确保双语文档一致”容易让人以为命令会检查译文。维护说明可以这样写：

> 核对两篇正文后，运行 `python3 scripts/check_docs.py --record docs/README.md`。命令会把两份正文当前的哈希写入 `docs/README.i18n.yaml`。

译文可以换语序、拆句，用目标语言里开发者熟悉的说法。字段、命令、操作对象和先后顺序要保留。上例里的“核对……后”决定了命令该在什么时候运行，翻译时不能省略。

<a id="review"></a>

## 核对与记录

更新配对记录前，先单独读一遍改过的译文：能看出谁在什么条件下做什么吗？再对照另一版，核对“必须”和“可以”、失败时的行为及例外。例如，把“取消当前轮次”译成“取消整个会话”，即使两边示例完全一样，读者也会写出两种实现。发现这种差异，先改正文。

核对完成后，从仓库根目录运行以下命令，把路径换成实际改动的英文文件：

```sh
python3 scripts/check_docs.py --record docs/README.md
python3 scripts/check_docs.py
```

第一条更新指定文档的配对记录。第二条检查全仓文档配对，会报告缺失的译文、过期的记录，以及结构、链接目标和示例上的差异。
